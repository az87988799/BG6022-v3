# BG6022-v3 结构性重建总方案

**版本：SR-1.0｜制定日期：2026-09-19｜状态：拟实施，未执行重建、未修改仓库。**

本方案服务于一个目标：用户通过自然语言提出化学问题，Agent 判断解释、查询、计算或澄清；把 ORCA 请求绑定到正确对象、方法与步骤；经授权执行；交付可追溯结果和解释；支持续聊，并通过统一接口扩展能力与方法。

本方案继承 V3，不从空白项目重写 ORCA 底层。软件以后可以称为 V4，但版本命名不改变代码继承策略。R0–R8 仅用于开发与验收，不进入运行时类名、状态或科学数据格式。

## 1. 最终交付目标与非目标

### 1.1 目标分层

| 层次 | 必须达到的行为 |
|---|---|
| 自然语言 | 中文优先，兼容英文名称、SMILES、CID、分子式、用户主动导入 XYZ；支持解释/查询/计算/澄清/修改等组合 |
| 科学请求 | 每个对象有独立身份约束；同一对象可重复计算；参数有任务作用域；未支持要求可见且不静默删除 |
| 授权执行 | 明确预览步骤、方法、对象、资源、输出与修复范围；按有效确认执行；修改后重新校验授权 |
| 数据与结果 | 数值、单位、文件、attempt、结构与方法来源可追溯；不让模型搬运计算数值作为下游输入 |
| 闭环 | 已支持的失败有界恢复；成功但前提不满足时不盲目前进；允许经过审批的后续计划修订 |
| 回答与续聊 | 事实、派生量、解释、限制分离；纯查询不重算；正确复用唯一历史对象；歧义时精确询问 |
| 扩展 | 新同类工具、完整方法 profile、外部后处理适配器可通过统一合同接入，并用新增功能的 diff 和真实链路证明 |
| 可使用交付 | Windows/Python 3.11 本地可安装聊天程序、状态/取消/恢复、真实文件入口、文档与证据；不是只有接口或测试 fake |

### 1.2 完成范围

核心发布必须保留并通过现有解析、RDKit 几何、ORCA SP/Opt/Freq、距离功能的验收，并完成单体系多方法、多对象独立任务、数值结果依赖、混合问答、证据解释和有界闭环。

扩展性发布必须至少增加：生产夹角工具、能量差工具、一个新完整方法 profile，以及一个受控外部转换工具。另一个未在核心开发中预先特判的简单工具作为冻结后的扩展测试。

受限溶剂和热化学属于独立扩展包，有单独门槛；不得把未完成的扩展包称为主版本已支持。Multiwfn 大范围功能、复杂反应网络、TS/IRC、激发态、构象系综、周期体系、Slurm、跨平台普适部署、多租户/计费不作为本次核心重建前提。

### 1.3 最终演示链

“先用已支持方法 A 优化乙醇；在同一个优化结构上用 A 和 B 分别计算单点电子能，展示结果并解释差异。”

后续连续验证：“只把第二个单点换成已支持方法 C”“列出刚才两个结果，不重算”“给我优化 XYZ”“这个结果能说明哪个方法更准确吗？”

完整演示要同时观察计划、授权、实际输入、进程启动次数、Result/Artifact 来源和回答，不只看聊天文字看起来合理。

## 2. 开发必须遵守的原则

| 编号 | 原则 | 可审计约束 |
|---|---|---|
| G01 | 保留科学底座、选择性重建上层 | input/runner/parser/checks 各保留一个生产权威入口；不能新写一套后长期双轨 |
| G02 | 保持七个持久对象 | Request/Plan/Step/Tool/Run/Result/Artifact；TaskSpec、SubjectSpec、ExecutionSpec、Claim 仅为嵌套值或临时协议 |
| G03 | 一个执行控制权 | 一个 worker/调用链负责 Run 推进；UI、模型和监测线程不能并发修改 Run；保留显式状态写入职责 |
| G04 | 模型建议，程序核验 | LLM 不执行 shell、不改源码、不决定科学成功，不替用户构造未经来源验证的分子和数值 |
| G05 | 保留原始科学问题 | 原话、身份、显式参数、禁止条件、结果要求有证据和作用域；不得为通过校验而删除要求 |
| G06 | 统一能力目录 | 参数、输入输出、前提、适用范围、展示和查询从同一目录派生；不得到处补工具名和字段名 |
| G07 | 确认是版本化授权 | 绑定 Request/Plan 修订、对象、参数、输入来源、资源、允许修复；陈旧“好的”不能批准新内容 |
| G08 | 所有执行有边界 | 有限时间、尝试、额外执行、输出和目录预算；取消需停止受控进程树，不能只停止等待 |
| G09 | 科学真值不可变 | 原始输入/输出和历史结果保留；新 attempt 新产物；未收敛几何可作受控 restart 候选但不得当成功结构发布 |
| G10 | 分开三种成功 | Tool 执行成功、科学目标满足、最终交付完整是不同状态；Result succeeded 不自动代表整个 Run 目标完成 |
| G11 | 重构按完整场景切片 | 每阶段产生可运行闭环；不先搭庞大抽象层再最后尝试 ORCA；移动文件与行为改变分开提交 |
| G12 | 不通过降低测试要求转绿 | 保留行为断言和原始样本；私有函数测试因接口变化可重写，但说明等价映射与新证据 |
| G13 | 测试证据分层 | fake 只在测试；静态检查、离线、真实 LLM、真实工具、真实端到端、人工审查各自报告 |
| G14 | 参考不等于实现 | 不把 AutoDFT 的规则/成绩、TritonDFT 的 QE 能力或官方软件功能当作项目已支持 |
| G15 | 小型可回滚交付 | 每阶段独立提交、支持范围、迁移策略、证据和回滚点；用户接受之前状态为 awaiting user acceptance |
| G16 | 输入和来源不变成指令 | 网页、检索片段、分子来源和日志都视为数据；防路径越界、命令注入、密钥泄露和越权出网 |
| G17 | 真实新发现不被“修正”为预期 | 不因结果与常识/文献不符就更换方法、改电子态或丢弃结果；区分数值恢复和科学假设改变 |
| G18 | 先证据后接口 | 新接口需由一个实际新增工具或已知缺口驱动；不建设通用 Service/Kernel、插件市场、第二个工作流引擎 |

G01、G02、G04、G08–G09、G15 继承并细化当前 AGENTS.md。[S05] 其余是本次拟实施设计，不声称已经存在。

### 2.1 技术与资源基线

沿用 Python 3.11、Pydantic、httpx、RDKit、当前 ORCA 适用范围、uv.lock；不以重建为由同时换 Agent 框架、数据库和 UI 技术栈。[S06,S18]

| 约束 | 保持的示例值 |
|---|---:|
| ORCA 核数 | 4 |
| 总内存预算 | 1024 MB |
| MaxCore | 192 MB |
| 同时运行的计算 | 1 |
| 单 attempt 超时 | 1200 s |
| Run 活动时间 | 3600 s |
| 输出上限 | 64 MB |
| 工作目录上限 | 512 MB |
| 科学步骤最大 attempts | 3（总尝试，不解释为 3 次额外重试） |
| 额外 ORCA 执行上限 | 3 |
| 计划修订上限 | 2 |

等待用户不计入活动计算时间；工具、监测和恢复活动使用持久累计预算，恢复进程不能重置额度。模型调用另有全请求/Run 上限，所有内部重试一并计数。拟新增默认 max_plan_steps=12、max_llm_calls_per_run=20，R0 确认后写入配置；这些不是当前代码已有值，不能因额度不够自动扩大。未启动 Run 的 intake/问答按请求单独限界。

MaxCore 控制的是每核主要工作区，不是整个程序硬内存上限。复用并验收 Windows 进程树限制，报告实际可观察的内存指标；不足时停止，不自动提升资源。[S19]

## 3. 目标结构与模块职责

自然语言 → 临时对话动作 → 对象/参数核验 → Request 任务实例 → Plan 目标与依赖 → 逐步细化/预检 → 授权核验 → 单一 Tool 执行循环 → Result/Artifact 与科学检查 → 接受/恢复/提出修订/澄清/停止 → 事实和证据回答。

### 3.1 持久对象的职责

| 对象 | 拟定职责 |
|---|---|
| Request | 原始问题、subjects、tasks、requirements、显式与禁止参数、answer_goals、schema_version、修订来源 |
| Plan | 一个版本的候选/已批准步骤图、任务到步骤映射、执行条件、需求覆盖；没有另一个独立 SkeletalPlan 存储系统 |
| Step | 稳定实例 ID、任务归属、工具、输入引用、有效参数及来源、科学前提、步骤细化状态；修订保留 origin |
| Tool | 参数/输入/输出/检查合同、能力范围、执行策略、preflight/prepare/execute/repair hooks 与展示元数据 |
| Run | 执行状态、等待原因、审批快照、budgets、attempts、修订/恢复/反思记录与当前结果指针 |
| Result | 一次 attempt 的数值、单位、检查、诊断、输入来源、输出引用和实际软件/解析器版本 |
| Artifact | 原始文件或结构化数据快照的类型、角色、位置、大小、hash、来源及 producer |

### 3.2 轻量模块拆分

保留 `agent.py` 作为门面和单一推进入口，不让它继续承担全部领域逻辑。新增名称均为拟议落点：

| 模块 | 拟定职责与约束 |
|---|---|
| `conversation.py` | 组合意图、pending 动作、指代与本轮 patch；延续现有 pending_action，不平行保留两套路由 |
| `planning.py` 或原 `planner.py` 的清晰子模块 | 任务提取、高层依赖、实例覆盖与逐步细化；迁移时只保留一个生产入口 |
| `bindings.py` | 输入字段/Artifact/历史引用解析，单位、来源和失效依赖 |
| `execution.py` | 统一 Tool 边界、策略委托、普通异常收尾；不是第二个 runner 或 scheduler |
| `reflection.py` | 基于证据的有界建议；无 Run 写权限、不执行工具 |
| `answer.py` / `output_contracts.py` | 数值事实渲染、证据解释、引用验证、逐要求交付 |
| `tools/*` / `orca/*` | 真正工具实现、确定输入/解析/科学规则；不依赖 conversation/answer 的内部逻辑 |
| `session.py` | 单一持久化入口、原子写、历史查询、schema 读取适配和恢复 |

ExecutionContext/ExecutionSpec 可为嵌套/临时只读视图和受限回调，不建立第八种长期对象。现有 ORCA Tool 会更新 Run.attempts 和保存 Run，因此要在 R1 明确写入职责，再逐步委托；不能误称“已有完全纯函数插件”，也不能让通用层和旧 Tool 双写同一 attempt。

## 4. 必须落地的核心合同

### 4.1 任务实例与参数作用域

Request 中的任务实例具有 task_id、subject_ref、capability_id、参数/来源、输入约束和输出要求。capability_id 只能来自注册目录。同名操作可出现多次，不能把重复次数隐式折叠。

参数先定位任务，再按优先级解析：本轮针对任务的修改 > 本轮明确全局修改 > 原任务显式值 > 原请求全局值 > 已公开并接受的配置默认/可信结构事实。charge/multiplicity 不从未经核验的模型建议推导；名称翻译保留原名，原话存在不构成结构等价证明。

计划验证从“扁平 operations 相等”改为：要求完整覆盖、每个实例唯一正确归属、所有额外步骤有必要性依据、满足用户先后/禁止条件、输入与输出类型相符。必要准备步骤可由性质需求推导，但必须在批准计划中可见。已有科学门禁不能靠删断言绕过。

### 4.2 类型化数值与文件依赖

InputReference 扩展为 artifact、step_port、result_field 三类互斥引用；用户直接输入的量单独标记 user_input，不能伪装成计算输出。模型只提交目录内引用，不能提交复制的计算数值。

验证分两次：计划时检字段、类型、单位维度和 DAG；执行时绑定具体成功 attempt、result hash、geometry hash、对象、电子态、方法与环境。首次运行消费上游后把绑定冻结为 Result provenance；重跑导致新 attempt 时依赖结果全部失效，不能“自动选择最新文件”。

能量差首批仅 `method_difference` 和经验证范围内的结构电子能比较，区别电子能与自由能、方法数值差异与准确性。反应计量、混合层级自由能和系综后置。数值转换使用有限已测试单位表，禁止任意模型表达式替代来源合同。

### 4.3 单一能力目录

声明用途、参数及作用域、所需输入、公开输出字段/端口/单位/shape、前提和检查、支持方法/版本/元素/条件、风险与资源策略、可用性、结果展示和查询信息。implemented、dependency_available、validated_for_scope 分开。

方法同样来自完整 MethodProfile，不能把泛函、基组、色散、溶剂任意拼接成“已支持”。更换 profile 必须体现在有效参数、输入、输出核验和报告中；没有验证范围的版本不能默认为全部版本可用。

### 4.4 版本化授权与按需细化

第一版尽量在确认前确定科学参数；仅未来几何/结果引用延后解析。审批快照保存目标 producer/port 和约束，真正启动前验证 materialized Artifact。动态绑定到已批准上游产物不等于任意更换文件。

新增步骤、修改方法/电子态/环境、扩大预算或改变科学目标必须重新确认。最初允许的有限修复如符合白名单，可继承修复授权；设置更严格但用户未授权的数值参数，也先展示差异，不以“更准确”为由越权。

模型确认只可匹配当前展示的 Request/Plan revision；用户改变对象后之前的“确认”失效。请求/模型调用/工具启动都带去重标识；进程恢复不承诺理论上全场景 exactly-once，而是可审计地防止盲目重复启动和误杀非本程序进程。

### 4.5 闭环与科学质量

规则负责退出、完整性、收敛证据、身份和前提检查；模型基于有限证据提出 accept/propose_retry/propose_plan_patch/ask_user/stop。模型不能将 not_met/unverified 改成 passed。

成功但异常的结果也保留原值。反思用于判断是否值得进一步验证，不是为了把计算“调到预期答案”。不能删用户要求、降低收敛标准、换方法或改电子态来刷成功率。程序不接受任意字符串 condition；条件必须引用已声明科学检查。

规则监测频率由本地任务长度与资源限制决定，不照抄 VASP 的十分钟间隔。模型仅在明确事件、诊断需要或有限兜底条件触发；简单任务无强制多轮反思。token/修订/attempt 耗尽时停止并给出现状，不默认接受。

### 4.6 回答合同

回答分为 Verified facts、Derived facts、Interpretation、Limitations。保留现有 output_refs 数值和文件保护；新的解释附 evidence_refs 与简短理由，数值和方法条件由程序插入。不能因为有引用 ID 就宣称语义已证明。

先用结构化 Result 做直接查询，再检索原始输出/文档片段补充解释；输出文件、run、attempt、行范围和 hash 一并绑定，旧失败日志不能混成最新成功证据。资料检索以现有 Tool/Artifact 记录证据，不新建文献执行框架。

一般知识回答允许明确标识为概念解释；请求版本、适用方法或资料出处时用受信资料库。首版章节/全文检索即可，无向量数据库要求。检索结果是数据不是系统指令；任何隐私外发需遵守配置与用户授权。

### 4.7 历史、部分结果与迁移

新写入只有一种规范 schema；旧结果、原始输入和产物不原地修改。提供一个只读旧记录适配器，使旧成功/失败结果可查看、可经校验显式导入新任务。无唯一映射时报告不兼容，不猜。

推荐不在第一版自动续跑旧格式等待/运行中任务：保留快照，先确认旧进程已处理，用户可显式导入数据建立新请求重新确认。此处是对旧方案的范围收缩，须在 R0 获用户接受；不删除旧任务。若跨版本续跑仍被要求，单独增加迁移验收，不默默省略。

Run 继续使用既有主要状态，waiting_for 增加清楚的等待原因。科学状态仍 passed/not_met/unverified；交付 complete/partial/failed/cancelled 与 Run 分离。文件交付失败不能把计算成功改成没算过，更不能补造链接。纯查询布局或语言改变不触发 ORCA。

所有阶段都先给具体小阶段任务，再实现、验证、提交/推送并报告等待用户验收。计划批准不等于用户授权一次实现全部阶段；实际仓库写入按当次任务和权限执行。

**本阶段不做：** 换模型/框架/数据库；同时新增计算能力；为消除告警而关掉全部日志。

### R1：收拢执行边界，保留并保护 ORCA 底座

**依赖：** R0。**目标：** 新上层可以通过稳定 Tool 合同调用现有真实 ORCA，实现成功、失败、取消、超时和异常的一致收尾。

**实施方案：**

| 工作包 | 内容 | 交付物 |
|---|---|---|
| R1-01 | 给既有 ORCA 输入/执行/解析/检查建立特征测试；记录哪些函数可保留、哪些仅需接口适配 | 单一生产入口与职责图 |
| R1-02 | 在 Tool 增加/整理 preflight、参数准备、执行策略和失败分类 hooks；主循环不再按具体引擎名准备参数或分配预算 | 轻量 Tool 接口、ORCA 适配实现 |
| R1-03 | 统一普通 Exception 到结构化失败；区分用户取消、预期计算失败、依赖缺失和内部错误；写盘失败不冒充已保存 | 失败合同、诊断 Artifact |

**主要文件：** agent.py、models.py 的 Tool、tools/orca.py、session.py、orca/runner.py、orca/windows_job.py、config.py；可新增 execution.py 作为委托边界，不新增第二个 runner。

**接口选择：** 先可沿用 execute(step, run, cancel) 兼容入口，把准备与预算策略移出 Agent。最终适配器仅能通过受限上下文获取当前输入、attempt 目录和写入回调；不要一次性要求全部工具改成纯函数。旧 Tool 与通用层不能同时分配 attempt 或各自持久化一份“当前结果”。

**验收方法：** 注入执行前、子进程启动后、输出检查时、结果提交时的故障。验证任意普通异常不会留下无解释的 running；确认过期或重复点击不会多启动。取消时检查整个受控进程树；未确认终止时标 interrupted/需核验，不伪报干净取消。保留原始输入/输出，使用现有小分子 SP、Opt、Freq 测试验证科学语义无退化。

**验收门：** 同一 ORCA 实现经新入口运行；离线和 Windows 生命周期测试全通过；至少一条获授权的真实 ORCA 小计算经新边界成功，相关 Opt/Freq 解析和科学检查回归通过。完整真实矩阵在 R8 再验。没有外部运行条件则真实门保持 blocked，不宣布本阶段科学验收完成。

**本阶段不做：** 更改泛函/基组或放松收敛标准；把异常抓住并打印一句话当作完整修复；多引擎/并行调度。

### R2：任务实例、多对象与逐任务参数

**依赖：** R1。**目标：** 用户可以在同一请求中指定重复操作、不同对象、不同方法和明确依赖。

**实施方案：**

| 工作包 | 内容 | 交付物 |
|---|---|---|
| R2-01 | Request 加 schema_version、subjects、tasks、requirements、answer_goals；Task/Subject 是嵌套合同，不是新持久实体 | schema 与新旧示例 |
| R2-02 | Step 绑定 task_id 和 subject_ref；支持同类型多个实例；稳定 ID 不随拓扑排序改变 | 任务到步骤映射 |
| R2-03 | 参数先按任务作用域归属，再解析优先级；记录原话/默认/结构事实等来源；q/M 独立校验 | 参数解析和冲突测试 |
| R2-04 | 将 operations 列表比较和单 distance 限制替换成实例需求覆盖、类型依赖与禁止条件校验 | 计划覆盖报告、拒绝原因 |
| R2-05 | 自然语言 Intake 和 Planner 同步支持新合同；旧写入停止，旧读取通过一个兼容入口 | 新请求端到端入口、兼容读取 |

**主要文件：** models.py、planner.py、tools/registry.py、agent.py、molecule_identity.py、orca/profiles.py 参数解析入口、session.py 的旧格式读取适配。

**必须处理的细节：** 对象身份约束按 subjects 隔离，不扫描整句话后把第一个分子式施加给所有对象；同一 subject 的几何角色也需区分。任务级方法不能被另一任务修改覆盖。“全部改成 A”才具有全局作用；全局 patch 与局部 patch 同轮冲突要澄清。charge、multiplicity 的结构推导在对象更换后失效。

**验收方法：** 同一固定 XYZ 上用当前已支持的两个 profile 分别 SP，计划含两个实例、实际 ORCA 输入方法分别正确、输入 geometry hash 一致。验证 Opt(A)→SP(B)、两个对象各自一次 Opt、只改第二个 SP、不允许额外 Freq、同一结构多次距离、未知方法不被替换为默认等场景。

**验收门：** 所有任务、对象和参数作用域合同通过；至少一条真实自然语言“两方法 SP”链到达两个真实 Result（依赖和资源需满足已验证范围）；旧单任务入口不退化。不能仅在 Python 中手工构造两个 Step 就宣告自然语言支持完成。

**本阶段不做：** 不受限批量任务、无限循环、自动计算反应网络；删除覆盖断言以便任何 Plan 都能运行。

### R3：数值结果依赖、来源与统一能力目录

**依赖：** R2。**目标：** 文件和数值都能作为可验证的上游输入；新增结果与参数由统一目录驱动。

**实施方案：**

| 工作包 | 内容 | 交付物 |

| R3-02 | 消费时绑定成功 attempt、结果与关键产物 hash、对象/方法/电子态；历史引用先验证再导入 | 只读值视图与 provenance |
| R3-03 | 统一公开输出与可消费输入目录；同属性多生产者必须通过任务引用区分 | 目录导出与碰撞测试 |
| R3-04 | 参数、输入、attempt 或方法变化时，使受影响下游失效；独立分支保留 | 失效图、重复确认与复用测试 |

**主要文件：** models.py、output_contracts.py、tools/registry.py、bindings.py、planner.py、session.py、tools/energy_difference.py；输入消费方不能自行遍历 Run 内部记录猜“最新结果”。

**验收方法：** 用 R2 产生的两个真实 Result 字段求差值；独立离线核对数值和单位。将一个源文件篡改、替换为失败 attempt、删除、换单位、换对象或换几何，应在消费前阻断。多个 SP 的 electronic_energy 必须选择具体任务；不能只按 property 找第一个。参数修改后只重跑受影响任务和下游，展示/语言变化不重算。

**验收门：** 下游输入中没有模型抄录的计算数值；生产者引用固定且可审计；完整性反例全部通过；自然语言请求能够生成差值工具调用并得到可追溯输出。不同方法的数值差不被解释为“低能方法更准确”。

**本阶段不做：** 任意 JSONPath、任意 Python 数学表达式、全局透明缓存、混合层级自由能、广义反应能。用户直接提供量可单独标记为 user_input，但不混作已计算证据。

### R4：自然语言、多轮动作与历史续聊

**依赖：** R2、R3。**目标：** 用户不需要了解 Tool 名、内部 ID 或固定句式，能够进行问答、计算、候选选择、精确修改与追问。

**实施方案：**

| 工作包 | 内容 | 交付物 |
|---|---|---|
| R4-01 | 在现有 pending_action 上统一组合动作，支持 query/explain/compute/supplement/replace/patch/new/control | 单一临时动作协议 |
| R4-02 | 身份补充保留原约束；明确替换才改变对象；参数更新与新请求分离；一个消息含修改+确认时先展示修订，不直接执行 | 动作/状态矩阵 |
| R4-03 | 以对象、角色、任务、最近交付定位历史，唯一时直接选；歧义时只问缺少的判别条件 | 可分页历史目录与候选快照 |
| R4-04 | 逐项保留未支持、冲突和缺失要求；缩减执行计划需明确批准；独立分支的部分执行需事先定义 | 需求状态与交付报告 |
| R4-05 | 状态/取消不排在长计算后等待；读快照、写入单归属；模型不可用仍能显示已保存结果和确定性状态 | CLI 控制与故障回退 |

**主要文件：** conversation.py、agent.py、planner.py、cli.py、session.py、prompts/intake.md、answer.py。禁止新路由包着旧 handle_message 再跑一次 Intake/Planner。

**验收方法：** 用相同语义的多种中文表述与混合英文术语验证：“给我刚才乙醇优化结构”“第二种方法保持不变”“先解释再计算”“我是在补充 CID，不是换分子”。旧身份等待中另开新计算，旧 Run 内容不变；候选快照过期不得误选。纯结果查询记录 ORCA 新启动数为零。原子索引先支持展示过的 1-based 编号；“那根 O-H 键”不唯一时请求具体原子，不由模型猜编号。

**验收门：** 固定关键动作反例全通过；真实 LLM 多轮测试成功但执行 stub 的部分明确标为语义验证；至少一组真实 LLM+ORCA 的澄清→确认→执行→追问链成功。语义明确的任务不能一律要求使用内部别名来换取测试通过。

**本阶段不做：** 多用户并发聊天、多租户、多轮修改正在写入的科学输入。运行中修改请求排队或先取消，不能就地改变正在计算的输入。

### R5：分层规划、事件监测与有界闭环

**依赖：** R1–R4。**目标：** 能根据上游实际结果细化下一步；能处理失败，也能处理程序成功但科学前提不满足的情况。

**实施方案：**

| 工作包 | 内容 | 交付物 |
|---|---|---|
| R5-01 | 在一个 Plan 中分开任务目标/硬约束与执行前参数细化；第一版未知的主要是未来产物引用，而非任意方法选择 | 分层 Plan 示例和 materialization 合同 |
| R5-02 | ORCA 规则监测输出有限进度与诊断；模型仅对明确事件或有限兜底介入；规则资源限制不受模型覆盖 | 监测事件/调用预算测试 |
| R5-03 | Result 后生成包含输入、收敛、检查、warnings、来源的摘要；反思只输出受限建议 | reflection.py 和临时建议 schema |
| R5-04 | 计划 patch 采用版本检查、dry validation、展示差异、确认、一次提交；保留稳定 origin 与累计预算 | 受控计划修订与回滚测试 |
| R5-05 | 修复同一科学问题时使用已批准白名单；涉及新方法/电子态/环境或新的计算步骤重新授权 | 数值恢复/科学变更分类表 |

**主要文件：** planner.py、agent.py、reflection.py、repair.py、orca/repair_rules.py、orca/runner.py、models.py 中 Plan/Run 嵌套记录、session.py；不增加第二个独立 SkeletalPlan 存储或另一个执行调度器。

**正确的状态顺序：** 保存一次 Result → 执行程序科学检查 → 评估对应用户要求/后续前提 → 需要时提出反思建议 → 校验/审批 → 推進或停止。不能在成功 Result 出现后，先由 `_requested_results_satisfied` 提前结束整个 Run，再事后补一段“质量分析”。同样不能先启动依赖步骤、再检查前提。原始成功 Result 不因后续 redo 而删除；只有当前可消费指针及需求状态变化。

**修订边界：** 可替换未执行步骤、在已有任务目标下插入已注册且必要的步骤、移除不再需要的可选准备步骤。不可删除用户硬要求，不可把自由文本 condition 当布尔值，不可插入额外执行去“确认文件可解析”。必要检查优先用已有文件和规则，不额外启动 ORCA。新模型建议的 accept 无权覆盖 not_met/unverified。

**验收方法：** 建立三类完整链：已授权 r2scan3c 故障→允许的数值修复→成功；Freq 完成但 local_minimum_supported 不通过→下游 gated SP 不启动；允许的修订被批准后执行且产物可追溯。后两类控制规则可先用真实归档输出回放加测试执行器验证，需与 live 科学证据分开。再做至少一个资源可承受的真实恢复场景，不保证任意失败都能修好。

**验收门：** 预算、尝试或修订用尽不会默认接受；异常结果保留；旧审批不能授权新科学问题；超预算 patch 被拒绝；同一失败不重复无限提问/重试。闭环机制必须在含成功后前提失败的测试中实际改变控制流，不能只有提示词和一段解释。

**本阶段不做：** 复制 VASP 十分钟监测阈值、无限自主研究、任意扰动几何代码、为了符合常识而调整方法“造出预期结果”。无法判断的科学现象向用户报告，不冒充模型已经证明真伪。

### R6：可追溯结果解释与知识问答

**依赖：** R3、R4；在 R5 完成后总体验证。**目标：** 既保持数值与文件可验证，又能解释结果与限制；知识问题能按需引用可靠资料。

**实施方案：**

| 工作包 | 内容 | 交付物 |
|---|---|---|
| R6-01 | 保留 reference-only 事实渲染；新增独立解释区，以 evidence_refs 绑定论据；方法、单位和检查状态不由模型改写 | 回答协议和渲染测试 |
| R6-02 | 优先查询结构化 Result，再读取绑定的原始输出行；按 run/step/attempt/hash 校验引用 | 原文证据定位和选择测试 |
| R6-03 | 接入小型版本固定的资料库，用现有 Tool 执行检索，用 Artifact 保存片段与来源 | knowledge_search Tool 与资料索引 |
| R6-04 | 动态形成科学限制：单点/优化/频率检查的结论范围，依据该对象/方法/几何/电子态相容性判断 | 结论模板、禁止误述回归 |
| R6-05 | 专业人员标注一组解释与引用问题；模型评审仅辅助，不以另一个模型分数代替事实验证 | 人工评审表与失败例集 |

**主要文件：** answer.py、output_contracts.py、prompts/answer.md、tools/knowledge_search.py、session.py，必要的本地 docs index；不需要新向量数据库或全文自由回答替代规范 Result。

**验收方法：** 查询原能量/XYZ 不重算；“为什么不能凭这个结果判断方法更准确”能解释但不编数；有频率证据时总体限制正确，方法不同或几何来源不兼容时不得拼接成通过。引用指向不存在 ID、错 attempt、错行号、被篡改文件时阻断相应声明。模型掉线或 JSON 无效时程序仍交付现有事实，解释部分明确未生成。

**验收门：** 固定数值/单位/方法/科学状态事实全部来源可核验；文献引用实际存在且支持对应句子；一般解释按专家标注集审查，不宣称自动形式证明。无来源不能伪造来源；证据不足不触发未经批准的额外计算。

**本阶段不做：** 将任何可检索文本都当科学真值、把模型自报 confidence 当授权、开放任意互联网文件读取、将数值正则扫描当作语义正确性证明。

### R7：用真实新增能力证明扩展接口

**依赖：** R1–R6 合同稳定。**目标：** 验证不是“现有六个工具能跑”，而是新增同类能力不需要改核心编排。

**实施方案：**

| 工作包 | 内容 | 交付物 |
|---|---|---|
| R7-01 | 将现有测试夹角工具的能力以正式 Tool 接入，输出标量、选中原子记录、CSV | 生产工具、单元/live 测试 |
| R7-02 | 冻结核心入口后，由独立任务新增一个二面角或几何汇总工具，不预先在主循环写特判 | 冻结 SHA、扩展 diff 审计 |
| R7-03 | 增加一个经过验证的新完整 ORCA profile；注册只允许通过该范围的环境/元素/操作 | 方法验证矩阵和输入/输出证据 |
| R7-04 | 接入一个受控外部后处理，如 orca_2mkl；先由合法 ORCA 计算保留、注册并核验 GBW，再转 Molden | 输入产物链、可执行版本、真实输出 |
| R7-05 | 完成工具开发说明和安装/可用性诊断；从一个声明导出模型目录、校验、展示和历史查询 | 扩展指南、接口合同测试 |

**主要文件：** tools/geometry_angle.py、新简单工具、tools/orca_conversion.py、orca/profiles.py、单一注册入口、相应局部适配/解析器和测试。现有 Tool 增加波函数端口时也需声明与验证，不假设 XYZ 已包含波函数。

**方法候选：** 可选 B3LYP-D3(BJ)/def2-TZVP 作为开发验证样例，而不是准确性推荐。只开放在当前预算与安装版本上实际验证的范围；若原候选不适用，记录原因并由阶段范围决议指定替代，不悄悄用旧方法冒充新增方法。

**验收方法：** 工具通过“不直接说工具名”的自然语言请求被选中并执行，完成结果、CSV/文件和追问。报告新增涉及哪些核心文件；同类扩展允许改一个组合注册位置，不允许在 Agent、Intake 路由、历史查询和 answer 中散布工具名分支。新基础数据类型确需改 output_contracts 时，单独说明类型的通用性与边界，不包装成无核心修改。

**验收门：** 本地工具、新 profile 和真实外部转换均至少一条完整链通过；方法参数与真实输入/输出一致；外部程序未安装或缺合法输入时标 blocked。外部转换通过只证明该类适配器，不代表第二个量化引擎或全部 Multiwfn 已打通。

**独立后续包：** 一个受限 CPCM 溶剂组合；受限气相热化学提取；cclib 辅助解析；Multiwfn 单一分析。每包有独立支持范围、真实数值/文件验证和问答验收，不在本轮一次全开。若用户把其中某包列为本次发布硬目标，则把其验收加入 R8，不能留在 optional 后宣告全完成。

### R8：完整产品交付与用户环境验收

**依赖：** R0–R7 通过工程验证。**目标：** 在用户实际环境交付可使用、可恢复、可追问和可扩展的程序。

**实施方案：**

| 工作包 | 内容 | 交付物 |
|---|---|---|
| R8-01 | 冻结发布候选，执行完整离线/Windows/安装包回归，在源码目录外安装并运行 | wheel、锁文件、安装记录 |
| R8-02 | 在冻结的自然语言开发集之外评测 holdout；固定模型/提示词/配置，重复运行 | 原始对话、分母和失败分类 |
| R8-03 | 在实际 ORCA 支持范围内跑真实小矩阵及至少三条完整多轮链 | Run/Result/Artifact 证据索引 |
| R8-04 | 验证取消、状态、进程/应用重启、旧记录只读和显式导入；移除已替代的生产旧路由 | 恢复记录、迁移和回滚说明 |
| R8-05 | 提交用户指南、能力矩阵、扩展说明、限制和验收报告；用户手工验收后记录 accepted | 完整交付包和阶段接受记录 |

**真实小矩阵：** 现有两方法在已验证的小分子范围内覆盖 SP/Opt/Freq；两方法 SP 同输入；Opt→Freq→受门禁 SP；Opt→距离/夹角；新 profile；真实后处理。并包括名称/SMILES/分子式歧义、取消和一个受控恢复。具体分子、charge/multiplicity、原始几何和容差在执行前冻结，不以本计划的示例替代实际科学设置。每个例子分开核验源结构身份与计算结果，不能拿 H₂ CLI SP smoke 覆盖中文 Opt→Freq 整链。

**最终人工链：** 用户发出一个多步骤请求，修改一次参数，批准；计算完成后索取两个结果、解释差异、取回文件；再用唯一历史结构发起新任务并取消。记录用户看到的输出与实际事件，检查是否发生未授权或不必要计算。

**验收门：** 第 7 节所有发布硬门槛通过；未完成可选项列入支持矩阵外；所有必需真实测试无 blocked。软件安装/升级后从目录导出的功能与实际可执行能力一致。工程已完成、已提交、CI 成功与用户已接受分别记录，不自行替用户验收。

**本阶段不做：** 为赶发布放宽科学成功条件、隐藏 benchmark 失败、以所有输出“看起来合理”代替真实输入/结果检查、删除旧科学数据以实现干净安装。

## 7. 统一验收体系

### 7.1 五层证据，不相互替代

| 层次 | 实际证明的内容 | 不能证明的内容 |
|---|---|---|
| 合同/单元 | schema、输入边界、参数作用域、依赖、授权、数值转换和状态规则 | 模型一定会正确理解任意自然表达 |
| 进程/集成 | 真实文件与进程边界、异常、取消、恢复；外部科学计算可用显式测试替身 | ORCA 的真实科学结果正确 |
| 真实 LLM | 实际模型的解析/规划/修订/回答协议；执行器可以用测试替身 | 该对话已经完成真实 ORCA 科学计算 |
| 真实工具/端到端 | 安装版本、实际方法、输入、执行、解析、产物链，以及实际多轮交互 | 全部化学体系、所有模型和任意方法普遍可靠 |
| 专家与用户 | 科学解释、引用支持程度、实用性、缺失问题与最终接受 | 形式化地证明全部自由文本没有错误 |

配套 acceptance_cases.jsonl 是 72 个基础场景的**验收规格**，不提供可直接运行的测试驱动，不是 72 项已通过成绩。实施者需将每项映射到真实 pytest 或人工/live 执行流程。现有测试继续保留，72 个场景不是总测试数量上限。

### 7.2 建议发布门槛

这些是拟定验收要求，不是目前项目成绩：

| 指标 | 门槛与统计口径 |
|---|---|
| 身份、授权、来源与科学检查硬反例 | 固定反例集 100% 通过；出现未授权启动、伪造数字/文件或质量门禁绕过则阻断发布 |
| 同对象多任务/参数作用域 | 固定合同集全部通过，比较规范任务与实际输入；不能只比较聊天答案 |
| 纯历史展示/追问 | 在指定“不重算”场景中 ORCA 新启动数为 0；派生新量需单独标为新 Tool 执行 |
| 自然语言语义+编排评测 | 至少 120 个冻结场景，可设 80 单轮+40 多轮，每场景重复 3 次；支持场景成功率≥95%，缺失/冲突/不支持场景的正确澄清/拒绝率≥95%，两种分母分开 |
| 误拒绝与多余澄清 | 单独报告；已明确且支持的请求不得通过一律拒绝满足“安全”门槛 |
| 真实 ORCA/后处理矩阵 | 冻结的必需矩阵全部按预先科学容差和产物断言通过；未执行、依赖不可用或超预算如实失败/blocked，不从结果表删除 |
| 证据解释 | 精确事实和引用完整性硬反例全部通过；专家样本无未修正的重大科学误述；一般性解释的限制和分歧保留 |
| 扩展性 | 生产夹角、新工具、新方法、外部适配按 R7 diff 规则和真实链路验收；不只检查 import 成功 |
| 安装与恢复 | 干净环境安装、源码目录外调用、重启读取和取消/恢复全部通过 |

真实 LLM+stub 的百分比只能命名为“语义/编排评测”，不能写成真实科学端到端成功率。另行报告实际 ORCA 端到端的 n、通过数、失败原因、模型/配置和资源。重复轮次不用于覆盖第一轮失败；三轮全部保留。网络失败单独分类，但不能在端到端总分母中无说明剔除。

冻结开发集与 holdout，调提示词时不能看 holdout 错例后继续把它算作独立测试。每次变更明确重验范围。小样本零失败不等于风险为零；测试不保证任意化学输入或自由文本绝对正确。

### 7.3 数值与文件的判定方法

数值容差按性质、方法、固定输入和安装版本事先指定，保存 absolute/relative tolerance 和选择理由，不在看到输出后放宽。跨平台浮点不强制逐字相等；同一 Artifact 的完整性必须精确 hash 匹配。

频率验收必须覆盖未完整解析、负值、缺失 Hessian、错误结构绑定等反例，不只找一个“正常终止”标记。能量差独立核对两个源量及换算因子；引用尚未通过的结果不可进入生产成功输出。科学前提还需检查对象/电子态/方法等条件，不能仅凭坐标 hash 相同就认定任意检查可互换。

### 7.4 可沿用的验证命令

下列参数由当前 pyproject.toml 和 tests/conftest.py 支持。[S18] 命令在实施者授权的项目环境运行，本次仅给出方案，未执行这些命令。实际工具路径不应写入仓库秘密信息。

```text
uv sync --frozen --group dev
uv run --frozen python -m pytest -m "not live_orca and not live_llm and not live_pubchem" --disable-socket
uv run --frozen ruff check .
uv run --frozen ruff format --check .
uv run --frozen python -m compileall -q src
uv build
```

实时测试分别显式启用，避免一次误启动所有昂贵计算。`<local-config.toml>` 是待替换占位符：

```text
uv run --frozen python -m pytest -m live_llm --run-live-llm --enable-socket --orca-config <local-config.toml>
uv run --frozen python -m pytest -m live_pubchem --run-live-pubchem --enable-socket --orca-config <local-config.toml>
uv run --frozen python -m pytest -m live_orca --run-live-orca --orca-config <local-config.toml>
```

涉及真实模型和真实 ORCA 的组合测试需同时携带对应启用开关；其标记和驱动由实施阶段添加并审查。不要把已给出的场景 JSONL 当作 pytest 已可运行的脚本。纯 ORCA 测试是否需要网络取决于具体测试，默认不扩大网络权限。

## 8. 阶段交付合同、分工与变更管理

### 8.1 每阶段固定交付

每阶段必须交付：目标与范围；涉及文件；旧→新合同映射；可运行的完整场景；测试命令与原始输出；真实/模拟/未执行标记；支持边界；已知问题；配置与迁移差异；回滚说明；基线与候选 SHA。

建议用 docs/reconstruction/stages/Rn.md 记录阶段计划和 docs/evidence/reconstruction/Rn-<sha>.md 记录验证。阶段号只用于文档与测试组织，不进入生产运行对象或文件协议。

证据包使用 evidence_template.json 的字段，并额外包含每个场景实际结果。关键字段：tested_commit、documentation_commit、branch、dirty_worktree、dependency_lock_sha256、effective_config_sha256、prompt_hashes、model、Python/ORCA/RDKit/解析器版本、fixture_mode、run/step/attempt、实际输入和结果 hash、授权摘要、时间/调用预算、测试退出码、失败与未执行原因、人工审查及用户接受状态。

本地未提交改动测试时记录 diff hash；提交后检查 tested tree 相同。仅补证据文档产生新 commit 可记录代码树未变的映射。代码、提示词、配置或依赖改变则必须重新评估影响和复验，不能把旧 live 结果重新贴到新提交下。

### 8.2 分工

实施者负责代码、可运行测试和明确未完成项；审查者检查合同、数据来源与权限边界，可使用独立上下文的代码审查辅助，但模型审查不替代运行证据；具有相应领域经验的人检查科学设置与解释；用户决定阶段范围、真实计算授权和最终接受。

不能让同一个生成模型只根据自己的自然语言总结给自己打分。关键成功条件由代码断言和真实 Artifact 检查支撑；人工部分保留审阅结论。

### 8.3 分支、提交与停止条件

默认从冻结开发 SHA 建立一条重建分支，保留历史标签/分支作只读回滚点。移动代码、合同变更、新能力尽量分开提交。通过本阶段门后再合入重建主线，合入 main 须按用户阶段接受与仓库权限执行。

一段时间可保留旧代码作为回归对照，但生产入口不能对同一请求同时运行两套计算。必要的 shadow 验证只比较计划/已保存结果，不重复启动真实 ORCA。已替换的旧入口在对应阶段完成切换并在 R8 清理，不能无限双轨。

以下任一事件立即停止该分支的能力扩张：未授权计算、身份被静默替换、未验证数值作为成功输出、质量检查被模型覆盖、取消未停止进程却报告取消完成、核心结果 hash/attempt 错绑。先复现和修复再继续。实际无法保存证据或控制进程时明确暴露限制，不能伪装成已恢复。

### 8.4 总方案不是一次性执行指令

本方案获确认后，建议首先只下发 R0，再下发 R1。每阶段实施请求明确起止范围、预算和可执行的 live 测试。当前请求仅要求制定方案，没有在本次对话授权或执行源码提交、推送、主分支合并、远程计算或用户数据迁移。

## 10. 完成定义

只有下面全部成立，才可认为本次结构性重建达到目标：在明确支持范围内，用户以自然语言提出需求，系统把对象、参数、步骤和结果目标完整落实；有效授权后真实执行；出现故障或未满足前提时正确停止、澄清或按批准范围恢复；交付可追溯事实和有证据范围的解释；追问不会无意改对象或重算；新的同类工具和方法经真实样例证明不需要修改核心循环。

“有类名”“有方法目录”“所有单测变绿”“模型能说出合理答案”“论文报告高成功率”都不单独构成完成。是否叫 V4 是版本命名问题；核心成果是清楚、可验证、可扩展的合同与唯一生产链。
