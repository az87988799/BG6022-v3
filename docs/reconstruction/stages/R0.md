# BG6022-v3｜R0 实施详细方案

**版本：R0-1.0｜制定日期：2026-09-22｜状态：拟实施。**

本文件是《BG6022-v3 结构性重建总方案》SR-1.0 的 R0 细化，不替代 R1–R8，不授权提前实现后续阶段。本次只制定方案与交接模板，没有修改远程仓库，没有执行项目测试、用户机器操作或真实化学计算。文中命令是后续实施参考，不是已经执行的记录。

## 0. 定位、依据与边界

R0 的交付不是新增计算能力，而是一份可以开始重建的、可复验的工程基线：开发者知道从哪个版本开始、哪些现有行为必须保护、哪些问题已知但未修、谁拥有状态写入权、允许改哪些文件，以及如何验收和回滚。

本次重新读取到：开发分支 `codex/v3-m3-extension` 为 `72b0c3cffe514a84d46dd681f8e3fb4f7aa9341f`；`main` 为 `79685f8adee3d25a92b3a9e57a8242be4522afe0`。开发 HEAD 的 offline Actions run `35189808853` 返回 completed/success。[S01,S02] 这只是本次查询事实；实施开始时必须再次核对。不能由 CI success 推出用户机器、真实 LLM 或 ORCA 全链已经通过。

总方案 R0 原有五个工作包保留：R0-01 基线与环境；R0-02 保留合同；R0-03 测试和构建；R0-04 缺口复现；R0-05 范围、授权及回滚。本文按 R0-A、R0-B、R0-C 组织操作顺序，不另建一套里程碑。[S03]

AutoDFT 的规划—执行—反馈设计是后续重建的参考；R0 不实现 Step Planner、Monitor 或 Reflector，不移植论文的 VASP 设置和预算。

### 0.2 本阶段的实现策略

默认路径是“文档＋测试＋环境隔离”，生产行为不变。唯一可选的生产代码整理，是把已有 `load_prompt()` 移到共享位置并更新实际调用方；该项不影响 R0 基础准备的完成，不满足前提则明确后置。

发现 RuntimeError、写盘失败或确认竞态缺口，R0 复现、登记并指定 R1 修复，不在同一提交中顺手改写执行循环。发现危及真实数据、越权执行或无法确认进程结束的情况时，停止相应真实操作；可以继续安全的静态审查和隔离测试，不能以“R0 已接受”批准生产使用。

## 3. R0-A：基线、单一依据与隔离

### R0-A1：先调查，不整理

**输入：** 用户实际本地仓库路径、当前已知基线。不得假定路径就是某个 E 盘目录。

**操作：**

1. 确认当前目录确属目标仓库；记录当前分支、HEAD、已暂存/未暂存/未跟踪文件及 worktree 列表。原始输出保存私有位置，提交摘要中的远程 URL 必须去掉凭据。
2. 检查是否有其他开发会话、正在运行的聊天程序或该项目的 ORCA 子进程。进程名只是线索，结合路径、PID、创建时间和已有执行记录判断；权限不足则写 unknown，不能写“没有运行”。
3. 未提交内容必须由拥有者明确决定：先保存为受审查提交、保留在原目录而本轮从已提交基线开始，或另行导入。未跟踪文件和本地配置不在普通 diff 中，要单独登记。不得自动 stash、重置、清理或杀进程。
4. 查询开发分支最新远程 SHA。与 72b0c3c 不同，先形成差异清单；确认哪些新改动应纳入，再冻结 `actual_base_commit`。不能直接忽略，也不能仅因发现更高版本就自动升级整个计划。

**只读调查命令示例：**

```powershell
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git status --porcelain=v1 --untracked-files=all
git diff --stat
git diff --cached --stat
git worktree list --porcelain
git ls-remote --heads origin codex/v3-m3-extension main
```

每个原生命令结束后立即检查 `$LASTEXITCODE`；失败不能继续使用空字符串作 SHA。`$ErrorActionPreference = 'Stop'` 本身不能替代原生命令退出码检查。不要把完整环境变量、密钥或含凭据的 Git 输出写入公共报告。

**退出条件：** 基线来源明确；所有本地差异已处置或被明确排除；真实进程是否存在已说明。发现活动任务时不在其工作目录切分支或修改依赖。

### R0-A2：一个新工作目录，不重新下载整套仓库

建议从已存在的本地仓库建立一个独立 worktree，分支名建议 `codex/structural-rebuild`。R0–R8 可在该分支上逐阶段整合，默认不需要每人一套长期分支。

在 A1 完成、提交对象已取得且基线确认后，实施动作示例为：

```powershell
# 先核实 FETCH 的远端和结果；这是本地取回，不是 push。
git fetch --no-tags origin codex/v3-m3-extension
# 仅在实际选定基线仍为下面 SHA 时使用。
git worktree add -b codex/structural-rebuild ../BG6022-rebuild 72b0c3cffe514a84d46dd681f8e3fb4f7aa9341f
```

分支或目录已存在时停止核对，不使用 `-B` 或 `--force` 覆盖。Git worktree 共享仓库对象并分开工作树的 HEAD/index，不提供 Python 环境、科学数据或主机资源的自动隔离。[S10]

基线 SHA 和一个明确的本地回退引用应记录在 preflight。可以使用已存在且不会移动的基线引用；额外标签非必需，不自动推送标签。Git 源码引用不等于数据备份。

**退出条件：** 新目录的已跟踪内容等于选定基线；原目录未修改。所有后续测试和开发从新目录执行。

### R0-A3：建立唯一开发依据，未批准事项保持待定

将用户实际提供并确认采用的 SR-1.0 总方案放到 `docs/reconstruction/master_plan.md`，保存输入文件 SHA-256 与方案版本。当前 `AGENTS.md` 仍指向作者机器上的旧总方案绝对路径。[S04] 更新其入口为仓库相对路径，但保留七个长期对象、Tool 边界、单 ORCA 实现、资源、失败和用户接受约束。

历史方案和里程碑只标注为历史，不批量移动或删除。详细阶段方案可细化总方案；涉及安全、范围和数据处置冲突时，先登记等待用户裁决，不由开发模型自行宣布新文件覆盖所有旧规则。

`preflight.md` 必须有范围决议表：

| 决议 | 建议 | 没有明确接受时的行为 |
|---|---|---|
| 继续继承 V3 而非全量重写 | 延续现有总方案 | 不建立空白 V4 执行底座 |
| 旧格式活动 Run 不跨版本续跑 | 首版旧结果只读、验证后显式导入新请求 | 不迁移、不删除、不续跑；R1 修复不受影响，数据迁移相关阶段仍有决议门 |
| 真实 PubChem/LLM/ORCA 调用 | 按当前阶段与具体样例单独接受 | 只做离线测试及可用性调查，不外发请求或开算 |
| 拟新增 max_plan_steps=12 / max_llm_calls_per_run=20 | 源自总方案的候选政策 | R0 只记录 proposed/accepted/pending，不写入尚无实现的严格配置模型 |
| 可选 prompt loader 抽取 | 小而可回滚，有基线证据才做 | 直接后置，不阻挡必要 R0 准备 |
| 推送目标 | 实施任务确认后推送重建分支 | 不合并 main、不强推、不删除旧分支 |

“请给方案”不等于实施或执行收费 API 的授权。后续“执行 R0”也不等于接受所有待定的迁移/预算选择。

**退出条件：** 新开发者仅靠仓库内文档就能定位当前方案与当前阶段；每个待定决议有最晚需要决定的阶段。

### R0-A4：隔离环境、配置、数据和证据

沿用项目 Python `>=3.11,<3.12` 与当前锁文件。[S05] 不把 Python 3.14 的离线通过当成目标 Windows/Python 3.11 环境已完成。

建议工作目录有独立 `.venv`；开发配置、测试运行数据和证据都放到新建的仓库外目录。路径由本机现状确定，记录解析后的绝对路径及用途，不照抄其他机器的 E 盘。

**隔离检查：**

- 检查 `VIRTUAL_ENV`、`UV_PROJECT_ENVIRONMENT`、`PYTHONPATH` 等特定变量是否把新目录指向旧环境；只记录需要的白名单字段，不导出全部环境变量。
- 实际开发 data_root 不得与旧 data_root 相同，也不得通过符号链接、junction、父子目录嵌套落入旧记录树。不能只比较未解析的路径字符串。
- 每次复现使用独立 tmp_path。不会把用户原 Run 加载后改写成失败或测试数据。
- 不复制整套大体积运行目录；只在获许可后复制必要的小型样本，带来源与 hash。对活动文件的在线复制不能冒充一致快照。
- 真实 ORCA 在整台开发机器上统一串行安排。当前 RuntimeLock 以 data_root 为作用域；不同目录的锁不能当作全机并发锁。该点沿用前轮代码审查，实施时再次确认。[S09]
- 默认保持 4 核、1024 MB、MaxCore 192、并发 1，attempt/run 时间及现有次数预算保持不变。[S08]
- Git fetch、依赖下载安装、PubChem、LLM、ORCA 分别记录许可和状态。默认不开 live 开关。

**环境命令顺序：** 先确认 uv 已安装和版本；不存在则按许可安装或报告 blocked，不偷偷使用另一套依赖。然后执行 `uv lock --check`（不更新锁文件）及 `uv sync --frozen --group dev --python 3.11`。前者失败先分类，不能去掉 `--check` 重锁。[S11]

`--frozen` 只使用现有锁文件，不代表已核验它与项目元数据一致；因此把 `uv lock --check` 与同步分开记录。[S11]

**退出条件：** 实际解释器、环境路径、包版本、开发 data_root 和证据根可核对；旧环境和数据没有被修改；依赖不足对应测试标记 blocked，不伪造版本信息。

## 4. R0-B：测试基线、保留合同与缺口

### R0-B1：先记录原始基线，再新增测试和整理代码

先在未做生产代码变更的选定基线上运行。保留当时源码、提示词、配置和测试集合的 hash；不可先修代码再把结果称为“原始基线”。

至少记录：测试收集数、选择表达式、nodeid 清单、平台、通过/失败/跳过/xfail/xpass/未选择数、命令、退出码、时间和日志路径。

**推荐命令：**（`$EvidenceRoot` 为已创建的仓库外目录；逐条保存输出和退出码。）

```powershell
uv run --frozen python -c "import sys; print(sys.executable); print(sys.version); assert sys.version_info[:2] == (3, 11)"
uv run --frozen python -m pytest --collect-only -q
uv run --frozen python -m pytest -m "not live_orca and not live_llm and not live_pubchem" --disable-socket -ra --junitxml "$EvidenceRoot\baseline-offline.xml"
uv run --frozen python -m pytest -m "windows_process and not live_orca and not live_llm and not live_pubchem" --disable-socket -ra --junitxml "$EvidenceRoot\baseline-windows.xml"
uv run --frozen ruff check .
uv run --frozen ruff format --check .
uv run --frozen python -m compileall -q src
uv build --out-dir "$EvidenceRoot\dist"
git diff --check
```

当前 CI 使用 `not live_orca` 并依靠 live 开关使其余 live 测试跳过；上面的显式离线表达式会把三类 live 都 deselect。两种统计不能直接比较通过数；记录筛选条件并按 nodeid 对齐。当前 conftest 有显式 `--run-live-orca`、`--run-live-llm`、`--run-live-pubchem` 和 `--enable-socket`。[S06,S07]

Windows 测试在非 Windows 上的 skip 不是通过；选择表达式零个测试不是通过。必要时复跑已确认的 `tests/integration/test_runner_windows.py`，但以实际收集列表和源码标记为准。新候选在 Windows 的等价 CI 可提供其执行证据；用户本机具体环境限制仍单列。

构建完成后，还需一个干净 wheel 安装冒烟：在仓库外新环境安装构建出的唯一候选 wheel，按锁文件导出的运行依赖安装，不用源码目录或 editable 安装替代。清除 PYTHONPATH 干扰，使用 `python -I`，核对导入位置在该环境 site-packages，再加载四个提示词并运行 CLI `--help`。不因为检查版本而无意执行 ORCA。

`uv.lock` 的运行/开发依赖冻结不能自动证明隔离构建环境中的所有工具版本已冻结；记录构建日志和实际能取得的 backend 版本，取不到的写 unknown，不把工作 `.venv` 中版本冒充隔离构建版本。

**退出条件：** 原始基线可复验；没有未解释的普通失败；构建包内提示词存在且能在源码目录之外读取。缺环境时允许交付部分报告，但不能标记完整工程准备通过。

### R0-B2：建立保留合同，不重复造测试

先读取并复用实际 tests。每项填写“合同 ID、行为、已有 nodeid、缺失断言、新增位置、真实/模拟边界、结果”。nodeid 必须来自 collect-only 或源码，不猜测试函数名。

| 合同 | 场景与必要断言 |
|---|---|
| BC01 新请求分流 | 旧身份等待中收到完整 Opt→Freq 请求；新 Run 建立、旧 Run 关键语义/状态不变、Freq 使用当前 Opt 产物、未确认 ORCA 启动数为 0 |
| BC02 身份补充 | 中文名称未找到后补英文名称或候选；同一 Run、原始身份与原目标保留、lookup 可更新、到确认而不是直接执行 |
| BC03 身份替换 | 明确更换对象后受影响结构与授权失效；没有明确替换时不能当成新身份 |
| BC04 词法边界 | SMILES 冒号后空格/全角形式；H20 不改成 H2O；不支持的分子式后缀不被截断成另一种输入 |
| BC05 候选与来源 | 错 CID、错异构体、过期候选或未验证来源不能发布成功分子产物 |
| BC06 授权 | 首次未确认不执行；更改科学要求后旧授权不能生效；参数被拒时无非法状态变化 |
| BC07 电子态和参数 | 非法类型、不完整值、否定/冲突陈述不能被模型改成合法整数；有效输入的来源可查 |
| BC08 原始结构 | 初始 XYZ 字节不覆盖；优化结构是新产物；输入 hash 与实际执行文件一致 |
| BC09 科学结果 | 未收敛或失败不提供成功输出端口；SP 能量、Opt 末态能量、Freq 与 Hessian 语义不混淆 |
| BC10 查询与交付 | 已有结果查询不增加计算 attempt；缺文件报告部分交付而不造路径、不重算 |
| BC11 日志 | 已知 RDKit 氢警告不刷屏但原始诊断保留；其他重要错误仍可见 |
| BC12 控制与恢复 | 明确取消、超时、旧记录读取与故障处理，观察实际进程事实和持久状态，不只看文字 |

特别注意：当前 `test_identity_supplement_updates_same_waiting_run_with_structured_intake` 替换了 `agent.advance`；它能证明身份续聊转换，但不能独自证明真实 advance 完成结构准备到确认。[S12] R0 应补一条不替换 advance 的离线链：仅替换远程来源和模型，保留真实 Request→Plan 校验、身份解析、RDKit 几何及 advance；在 ORCA 最低可观察启动边界安置哨兵，确认启动数为 0。

当前 `test_new_complete_request_is_not_swallowed_by_waiting_identity_run` 的旧等待对象为名称“水”。总方案的“等待 C6H14 时另发优化水并算频率”应作为补充 fixture，而不是称原测试已经覆盖该精确情景。[S12]

当前 RDKit 测试覆盖控制台过滤、文件日志保留、重复初始化不累加 handler 及 helper stderr 留存，可复用而不复制。[S13]

三类测试必须分开：

- 永久保护：授权、来源、单位、身份、不覆盖原始数据等，重构后必须继续成立。
- 当前限制：唯一 operation、单 distance 等，R0 不修改；R2 要替换为新合同测试。
- 新发现缺口：期望行为尚未满足，登记为缺口，不把当前错误行为冻结成永久正确要求。

**退出条件：** 所有关键已修行为有真实可定位的断言；缺口与旧限制清楚分开；未用 fake_advance 冒充完整状态推进验证。

### R0-B3：做小型依赖和写入清单，不建设新框架

重点扫描 Agent/Planner/Answer/ToolRegistry/session/ORCA Tool 和测试的跨模块导入、私有调用、状态写入、文件写入。使用 `git grep` 和必要的 AST 读取即可，不引入大型图数据库或依赖分析服务。

建议扫描词包括：`load_prompt`、`save_run`、`save_result`、`run.status`、`step_status`、`attempts`、`execution_permission`、`accepted_snapshot`、`accepted_execution_sha256`、`current_results`、`pending_data`、`plan.revision`。不要仅凭文字出现次数判定实际控制权，逐处核对上下文。

`preflight.md` 中至少有以下“当前—目标”表：

| 字段/职责 | 当前写入位置（须填实际函数） | 目标负责人 | R0 动作 |
|---|---|---|---|
| Request/Plan 与修订 | Agent/Planner 相关调用 | 唯一协调链 | 盘点，不迁移 |
| execution_permission 与授权 hash | confirm、修改路径等 | 单一授权校验入口 | 标出全部失效点 |
| attempt 号、prepared/started/finished | ORCA Tool 与其回调等 | 一处生命周期管理入口 | 记录写入顺序，不增加第二处 |
| Run/Step 状态、当前结果索引 | Agent 与 Tool | 协调链统一语义 | 登记双重处理风险 |
| PID、创建时间、进程退出事实 | runner 与回调 | runner | 保护原事实来源 |
| 数值和科学检查 | parser/checks/Tool | 领域适配器 | 不改科学语义 |
| JSON/Artifact 落盘 | session 及调用方 | 单一持久化入口 | 记录异常/原子性缺口 |

“目标负责人”是后续设计，不代表当前已迁移到位。R0 不创建空的 ExecutionService、Kernel、Store 来占位置。

每个已计划修改的核心接口写明：输入、返回、异常、是否有副作用、调用方、测试和后续修改阶段。只有主线需要的接口进入清单，不提前设计全部插件 SDK。

**退出条件：** R1 开发者能够按函数定位执行/授权/状态写入点，不会重复分配 attempt 或把 Tool 与 Agent 两套保存逻辑叠加。

### R0-B4：复现缺口，把失败变成有边界的 R1 输入

总方案要求 R0 做缺口复现而非抢先修复。[S03] 每项记录：gap_id、基线、触发点、最小 fixture、期待行为、实际行为、退出码/trace、持久文件快照、失败指纹、修复阶段和生产风险。

| 故障注入 | 实施方式 | 要观察的事实 |
|---|---|---|
| Tool RuntimeError / TypeError | 测试注册表中的测试工具抛出明确异常 | 是否越出工具边界，Run/Step 是否残留 running，是否错误交付成功 |
| 写 Run/Result 失败 | 只在 tmp_path 用 monkeypatch 或隔离 helper 注入 OSError | 是否停止后续执行；是否承认保存失败；不能要求磁盘不可写时仍保证落盘成功 |
| 取消与确认交错 | Event/Barrier 驱动的确定性时序；固定最长等待 | 是否产生重复启动或取消后启动；不靠长 sleep 碰运气 |
| 重复确认 | 模拟重复控制消息、记录启动边界调用数 | 同一授权是否被消费多次 |
| 下游产物缺失/变更 | 只删除或篡改测试拷贝 | 是否在使用前拒绝，而非返回已有成功标签 |
| 来源/模型中断 | HTTP mock/受控错误 | 是否保留原请求、有限终止、无凭空结果和意外出网 |

至少优先处理 RuntimeError/TypeError、写盘失败、取消/确认三组。每个用例要有短的外层时间界限和 finally 清理；不无限等待真实 ORCA，不修改原数据目录或人为破坏系统权限。

**已知红灯处理规则：**

1. 不把原来绿色的保护测试随便改为 skip/xfail。
2. 新增缺口测试先无标记运行并留存原始失败。测试表达期待的不变量，而不是把“卡在 running”当正确。
3. 确认为基线缺口后，允许仅对对应的新用例使用 `pytest.mark.xfail(strict=True, reason='R1-Gxx ...', raises=明确的失败类型)`；用例要验证前置条件与注入点，不能用泛化 Exception 掩盖其他错误。必要时给末尾已知不变量失败使用专门的 AssertionError 子类。
4. 使用 `--runxfail` 对精确 nodeid 复跑并保存实际失败记录；该命令失败是缺口证据，不把它伪装成正常验收命令成功。
5. 预期失败显示为 xfailed，不能计入 passed。XPASS 触发审查，不默认“忽然通过就完成”。R1 修复后删除对应 xfail。[S14]

**退出条件：** 所有失败有分类，关键缺口可安全复现并交给 R1。R0 允许“工程准备就绪、已知缺口待 R1 修复”，但不允许“安全缺口存在、仍准许真实使用”。

## 8. 附录：干净安装与命令记录要求

### 8.1 干净 wheel 安装示例

下面是实施用命令框架，实际路径变量必须先建立并核验。安装/下载需在允许范围内；不能绕过失败自动换源或升级。

```powershell
uv export --frozen --format requirements-txt --no-dev --no-emit-project --output-file "$EvidenceRoot\locked-runtime.txt"
uv venv --python 3.11 "$EvidenceRoot\wheel-smoke-venv"
$SmokePython = Join-Path $EvidenceRoot 'wheel-smoke-venv\Scripts\python.exe'
uv pip sync --python $SmokePython "$EvidenceRoot\locked-runtime.txt"
# 仅在 dist 中确认唯一的本次 wheel 后设置 $WheelPath，不使用可能命中多个旧包的通配安装。
uv pip install --python $SmokePython --no-deps $WheelPath
# 在新建的仓库外工作目录中运行以下命令，完成后返回原目录。
& $SmokePython -I -c "import bg6022; print(bg6022.__file__); from bg6022.planner import load_prompt; [print(n, len(load_prompt(n))) for n in ('intake','planner','answer','repair')]"
& $SmokePython -I -m bg6022 --help
```

实现者还应校验导入位置确属 Smoke 环境、四份提示词的 hash 等于基线/候选资源 hash。仅打印字符长度不够验收。`uv export` 与构建可能涉及工具版本差异，先核对已安装 uv 的 `--help`；当前支持选项以官方命令参考为依据。[S16]

### 8.2 命令日志必须有退出码

每条命令保存程序、参数、工作目录、开始/结束时间、真实退出码、stdout/stderr 的私有文件位置与 hash。使用 PowerShell pipeline 时在原生命令后立即捕获退出码，不能把 Tee-Object 成功当作 pytest 成功。预期红色 probe 使用独立记录，不与门禁正常命令混淆。

为收集证据可以编写一个本地一次性帮助脚本，但 R0 不要求建设自动化测试平台。脚本不得执行自动清理、强推、无限重试或未批准的 live 命令。
