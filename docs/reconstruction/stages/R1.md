## 0. R1 要交付的结果

保留现有自然语言入口、Request/Plan/Step 语义和 ORCA 科学实现，建立一个一致的执行边界，使已经合法的计划：

1. 在同一有效授权下不会因重复确认被重复执行。
2. 普通 Tool 异常、结果保存失败、Run 保存失败能停止后继步骤，并返回真实、结构化、可审计的状态。
3. 只有一个逻辑控制链推进 Run、分配 attempt、发布当前结果；外部进程由既有 runner 管理。
4. 参数准备、前置检查、执行预算及允许修复由 Tool 的局部适配策略提供，而不是主循环按引擎名分支。
5. 取消、超时、进程清理未确认、应用中断和残留 guard 都有明确处理；不因重启自动再执行一次。
6. 同一 ORCA 实现经过新边界完成至少一条获授权的真实小计算；Opt/Freq 输入、解析和科学检查不退化。

R1 是执行基础收拢，不是全部产品完成。自然语言多对象/重复 SP、result_field 数值依赖、混合对话新协议、成功后反思、知识库和新增方法分别属于后续阶段。

### 0.1 四个必须关闭的 gap_id

| 缺口 | 当前用例 | 必须实现 |
|---|---|---|
| R1-GAP-TOOL-UNEXPECTED-EXCEPTION | RuntimeError / TypeError 两个参数化 case | 工具边界结构化失败，Run/Step 收尾，原诊断保留 |
| R1-GAP-RESULT-PERSISTENCE | save_result OSError | 不发布未提交结果，不启动后继；明确保存失败 |

| R1-GAP-CONFIRM-RACE | 同一等待授权同时 confirm 两次 | 一次授权最多一个推进 owner；重复调用不重复执行、不取消先行调用 |

现有取消边界用例是已通过的保护，必须保持。R1 不以“xfail 数量减少”单独判断完成，而要使原问题的不变量成为普通通过测试。

## 2. 本次代码审查给出的实施起点

### 2.1 不要重做已经存在的底座

`orca/runner.py::run_orca` 已使用 Windows Job Object、CREATE_SUSPENDED、on_started 回调、进程组、取消/超时检查，具有普通 Exception 清理及 finally 二次清理。R1 要验证回调异常、写入异常和清理异常贯穿上层，不重造另一套 runner。

`session.py` 已有 RuntimeLock、ChatSessionLock、execution_guard、atomic_write_json、execution_fingerprint。RuntimeLock 是 data_root 作用域的物理执行互斥，不是 Run 授权的一次消费机制，也不是跨不同 data_root 的全机锁。

`Tool.execute` 及 ORCA Tool 仍使用 Step/Run；tools/orca、molecule、pubchem、geometry_distance 均可能参与 attempt/Artifact 记录。要逐个迁移写入责任，不能只改 Agent 然后让 Tool 继续独立分配同一 attempt。

### 2.2 R0 测试会受到的合理接口变化

- `test_duplicate_confirmation...` 在 `_acceptance_snapshot` 内设 Barrier。正确前置互斥后，第二次调用本来就不应进入 snapshot。同步点应改到公共确认竞争边界或 owner 获取前，先行 Tool 用 Event 保持活动，再检查另一确认返回已有状态/忙碌；不能要求两个调用都进入受保护临界区。
- save_run/save_result 当前 monkeypatch 在 `bg6022.agent`。提交逻辑迁移后应改为新权威写入口，继续断言注入命中次数与错误身份。否则旧 patch 不生效会出现假绿。
- 专用 Expected*Gap 类只用于 R0 记录已知错误。每个缺口真正修复后移除对应 xfail；必要时把末尾断言改为普通不变量断言，保留原始失败证据和旧→新 nodeid 映射。
- Run persistence 用例没有以前已提交成功步骤，所以 current_results 应为空。增加一个有既往成功步骤的用例，证明修复不会清空全部历史成功结果。

这属于测试与新接口等价映射，不得减少启动次数、授权、异常注入和持久化状态断言。

## 3. 目标职责与拟议接口

### 3.1 单一推进，局部委托

```text
CLI / chat / explicit API
    → 获取该 Run 的推进所有权并核验请求版本
    → 读取/检查实际 Run，检查取消与预算
    → Tool preflight / 参数准备（返回建议值，不自行改 Plan）
    → 需要输入或确认：保存等待点并返回
    → 校验有效授权、参数、输入 hash 和科学前提
    → 分配唯一 attempt，保存 prepared checkpoint
    → 既有 Tool 适配器 / 既有 ORCA runner
    → 构造 Result 与科学 checks，验证当前 attempt 归属
    → 提交 Result 与 Run 当前结果指针
    → 下一 Step / 等待 / 失败 / 取消 / 中断
```

这不是新固定 Opt→Freq→SP workflow。原有 Plan 组合和 goal_checks 保持有效；R1 不允许通过跳过科学前提推进。

### 3.2 责任归属

| 责任 | 唯一逻辑负责人 | 其他模块可以做什么 |
|---|---|---|
| Run/Plan/授权/等待状态 | 推进 owner 所在协调调用链 | UI 发信号/读快照；Tool 提交事实 |
| attempt 分配、预算保留、阶段 checkpoint | 一个共享 lifecycle 实现 | 适配器使用给定 attempt，不自行再计算 next_attempt |
| 参数科学准备与前提 | Tool policy 的受信代码 | 返回 prepared 参数/缺字段/诊断，协调方应用并校验 |
| 进程创建和停止事实 | 现有 runner | callback 经 owner 接口保存已观察事实 |
| 科学解析和成功条件 | 现有 parser/checks/Tool | 通用层不解读能量或发明成功 |
| Result 发布与 current_results | 一个提交函数，由 owner 调用 | 适配器返回候选 Result，不能独立发布当前结果 |
| 文件和 JSON 操作 | session 的统一存储函数 | 不在各模块各造原子写/重试机制 |
| 允许恢复选项 | Tool adapter/既有规则 | 模型只在允许集合选择；协调方校验和应用 |

### 3.3 接口建议（拟议，不是当前可调用 API）

只引入由已有缺口需要的轻量函数/临时值类型：

| 入口 | 输入与返回含义 | 边界 |
|---|---|---|
| Run advancement owner | 规范化 data_root、Run ID、短期 ownership token | 非阻塞竞争；拥有者在等待/终态释放；不得给第二个调用隐式重入权限 |
| prepare_for_execution | Tool、Step、已验证输入视图、当前配置 → prepared 参数或 needs_input | 不运行科学作业，不写 Plan；显式参数不变 |
| execute_owned_attempt | owner、Tool、有效 Step、cancel → Result/等待/受控失败 | 调度与异常边界的唯一入口，不是第二个 runner |
| commit_attempt_result | owner、候选 Result、候选 Run 索引更新 → 提交状态 | Result 与当前结果指针的顺序有定义 |
| close_execution_failure | owner、阶段、原异常、已有事实 → 失败/中断诊断 | 允许保存失败返回“未保存”，不无条件再写 |

`AttemptContext` 若需要，可为不可变/受限的临时对象，包含 run_id、step_id、attempt、目录、validated_parameters、只读输入、资源/剩余预算、Event，以及必要的 Artifact 注册和 checkpoint 回调。不允许任意遍历和修改所有 Run 字段。

不要求在一次提交中把全部工具改成纯函数。可以保留现有 `execute(step, run, cancel)` 和显式 CLI 兼容入口，但其生产生命周期写入必须委托到同一个共享实现。外部兼容入口没有 owner 时通过同一 gateway 获取；内部调用携带既有 owner，不能递归抢同一锁。方法名可以结合当前类型检查调整，角色和单一写入约束不能省略。

## 4. 核心合同一：确认与推进所有权

### 4.1 锁与授权解决不同问题

需要同时保证：

1. 同一 Run 一次只有一个推进 owner（线程、同进程不同 Agent 实例、同 data_root 的竞争入口）。
2. 确认绑定用户看到的具体修订和预览内容，而不是读取到一个布尔值就执行。
3. ORCA 物理执行继续遵守既有 RuntimeLock；二者不可互相替代。

可复用 session 现有平台锁实现，抽出最小共享锁原语后添加 Run 作用域锁，避免复制大套锁框架。新锁文件为技术同步文件，不是新业务实体。必须做规范化路径和 ID 校验、异常释放、重复进入规则及测试。

约定锁顺序：已有 chat 入口锁（若持有）→ Run 推进 owner → ORCA RuntimeLock。禁止逆序、禁止 callback 再次获取上层 owner。对象锁与 OS 锁均按当前平台验证，不能仅以一个 Agent 实例的 threading.Lock 宣称跨实例/跨进程防重。

### 4.2 确认的执行顺序

在会取消/替换当前请求 Event 的任何 `_begin_request` 等逻辑之前，先对重复确认进行 admission 检查；重复确认不能把已经正常运行的第一条请求取消。

取得 owner 后重新核对权威状态，不能使用锁外加载的旧 waiting Run 直接执行。只有当前 waiting_for=confirmation 且预览版本匹配时，才消费确认。

确认标识至少关联 run_id、Plan revision、preview/execution fingerprint。优先复用 existing pending_data/accepted_snapshot/accepted_execution_sha256，不新建授权数据库。未来产物未产生时，批准的是既定上游来源与规则，执行前再核对真实绑定。

CLI/UI 排队的确认应在入队时携带当时展示的预览版本，或在无法唯一判断时要求再次确认；不得排队后自动批准届时的另一版计划。保留兼容 confirm(run) 入口时，按当前有效且唯一预览校验，不声称能从任意旧自然语言“好的”推断其时间归属。

获得 owner、完成授权校验并成功保存授权 checkpoint 后进入内部推进。重复调用返回当前运行/终态快照，不新建 attempt，不修改授权，不抛未处理锁错误。

### 4.3 取消不能排队等待长作业

活动 owner 的 Event 必须在允许启动前可被设置。取消线程只发信号，不拿着陈旧 Run 改写活动状态。无人持有 owner 的 waiting Run，可在取得 owner 并重读后转 cancelled。

保持 R0 的“确认写入与启动之间取消→零次启动”。启动前最后一次检查取消；已生成进程则由 runner 停止并证明清理。不能持有一把阻止取消信号发送的长锁。

当前项目为单机单 chat。跨进程取消控制不是新增 IPC 项目；另一进程不能确认能取消时报告受控忙碌/不支持，不能假报取消。跨进程重复执行仍必须被拒绝。

### 4.4 不作不可能的精确一次承诺

本阶段保证并发和重复请求下的受控“至多一次推进/启动”，并对崩溃不确定窗口采取停止核验。不能宣称文件 checkpoint 与操作系统进程创建在崩溃时具有天然的严格 exactly-once 原子事务。

## 5. 核心合同二：错误、保存与结果发布

### 5.1 失败分类

保持现有测试中已使用的顶层类别，必要新增阶段/细分字段，不随意把每个底层库异常作为新的 Run 状态。

| 情况 | 建议顶层处理 | 不得做 |
|---|---|---|
| 输入缺失/可补充 | waiting/clarification | 泛化为系统崩溃 |
| 权限/参数拒绝 | 原 waiting 或明确失败诊断，零科学启动 | 自动更改方法或授权 |
| Tool 普通内部异常 | failed，category=execution_boundary，记录 type/stage | 越出后留下无解释 running；盲目 LLM 修复代码错误 |
| Result 保存失败 | failed，category=result_persistence | 发布尚未提交的 current result 或启动 successor |
| Run 提交失败 | failed，category=run_persistence（可写时落盘） | 声称已保存；把未发布指针当当前成功 |
| 已知 SCF/Opt 失败 | 保留 parser 分类和合法修复范围 | 统一吞成“代码失败”或放宽科学检查 |
| 取消且清理被证实 | cancelled | 仅发了取消信号就宣布结束 |
| 清理未确认/崩溃不确定 | interrupted，保留 guard 和诊断 | 清除 guard 并继续下一计算 |

普通 `Exception` 在执行边界收敛；KeyboardInterrupt 单独触发取消/runner 清理。不要 `except BaseException: pass`。SystemExit、进程终止等不可恢复情形需要 cleanup/finally 保证和下一次启动核验，不能冒充正常 Result。

### 5.2 失败响应不再依赖正常回答链成功

失败路径使用最小程序化回复，带 stage、类别、是否已保存、是否有未确认进程及下一步限制。不为了报告磁盘故障再调用 LLM、再追加会话日志，并因同一 OSError 遮蔽原异常。

异常信息保留私有、有大小界限的诊断；共享回答脱敏。诊断 Artifact 自身写入失败时返回 diagnostic_persisted=false（拟议诊断字段），不造文件路径。

返回接口可保留 Result|None 兼容形式，但调用方必须以当前 Run 和提交状态判断此次失败，不能拿上一步 last_result.succeeded 宣布整个请求成功。Answer/CLI 只作这一必要失败呈现适配，不扩展自由解释能力。

### 5.3 明确提交顺序

在 owner 下执行以下序列，结构可用普通函数实现，不引入新事务平台：

1. 保存执行前 prepared/checkpoint 和原有已提交 current_results 快照。
2. 由 Tool/runner 产生实际输出与候选 Result；校验 run_id、step_id、attempt、输入指纹、Artifact 归属、声明的输出和科学检查。候选不立即进入 current_results。
3. 通过 session 保存该 attempt 的 Result 文件；已有已提交 Result 不原地覆盖。保持原始科学状态与数值真实。
4. 生成候选 Run checkpoint，写 result_index、step_status、current_results 和本次 attempt 完成事实；原子替换 Run 文件成功后，才把对应索引视为正式发布。
5. 只有第 4 步成功且取消/科学前提允许，才推进后继。随后会话摘要和展示失败应区别于计算本身失败。

这是多文件之间的发布约定，不是把两个 os.replace 说成一个事务。可以用 staging/candidate Run 副本减少未提交状态泄漏；具体实现必须通过注入测试。

### 5.4 两种持久化缺口分别处理

**Result 写入失败：**不把本次候选放进 current_results；不启动后继。原始输出留存，可单独报告“计算输出产生但未可靠提交结果”；能写 Run 时记录 result_persistence，否则仅报告可观察故障并阻断执行。

**Result 已写、Run 指针写失败：**回退本次未发布的索引修改，保留以前已提交的成功步骤和新 Result 原文件。测试中此前没有已提交步骤，所以 current_results={}；有旧成功步骤时不能全清空。新 Result 暂不被当前图消费，后续显式核验可恢复索引，不重新做昂贵计算。

**Run 已提交、session/回答保存失败：**计算与已提交科学结果不被抹掉；交付或会话索引报告失败/部分，不能再次执行 ORCA。

### 5.5 磁盘持续不可写

最多执行一次明确的 best-effort 失败 checkpoint（不是重跑计算）。若该写入也失败，停止一切后续作业和成功发布，通过进程内诊断与 stderr/响应报告未保存；不要让 finally 无限 save_run 或覆盖原异常。

既有持久记录可能仍显示 running；这时必须明确“未能更新磁盘状态”，不能要求不存在的存储保证。恢复入口依 unfinished attempt/guard/原始事实进入 interrupted/需核验，直到存储与进程情况清楚。R1 验收看的是不假称落盘、不继续算、不丢原始事实，不是磁盘故障下仍强制生成文件。

## 6. 核心合同三：统一 attempt 与 Tool 策略

### 6.1 一个 attempt 分配入口

先校验授权、参数、输入、可用性和剩余预算，再由共享 lifecycle 分配 attempt 号和目录、登记尝试预算并保存 prepared。适配器和 runner 不再次调用自己的 `_next_attempt`。

每个尝试最多一份规范记录；prepared→started→finished 的更新顺序可审计。非法输入、重复确认/忙碌退出不消耗科学执行额度；已经保留的尝试在失败/恢复后不能随意清零。区分预算保留与实际 spawn 事实，pid/start marker 由 runner 提供，不由上层虚构。

复用 run.origin_step_map、attempt_counts、extra_orca_executions 和现有持久累计活动时间语义。计划修复不应换个 Step ID 或重建 Run 逃避原 origin 额度。等待用户不计活动时间；进程恢复不能重新给一整份预算。

### 6.2 适配器可分步迁移，但最终只有一条生产路

先为现有 ORCA 路径接入共同 lifecycle，再按同一接口迁移 resolve_molecule、generate_geometry、geometry_distance 的 attempt/status 发布。各工具的科学解析保持原位，只有记录写入委托。不要要求所有业务逻辑变成无副作用纯函数；Artifact 生成仍通过受控 callback 进行。

兼容显式 CLI 和旧 Tool 调用的 wrapper 必须委托共同入口，而不是原旧方法与新执行器各执行一遍。测试替身可以保留简单三参数 execute，生产注册表不得出现静默假实现。

### 6.3 Tool hook 的最小范围

在 Tool 中增加/整理运行时可调用的 preflight、参数准备、执行预算策略、允许修复策略。用明确的返回类型描述 prepared/needs_input/failure。运行时对象和 callable 从 JSON dump/能力描述中排除，公开目录仍只输出可序列化元数据。

现有 parameter_preparation / execution_budget 的字符串可暂作为兼容描述，但不能再驱动 Agent 中按 ORCA 名字分派的运行分支；必须有一个且仅一个实际策略选择入口。注册时检查实现与声明相容，不把未知策略静默当 none。

迁移 `_prepare_orca_step`、`_validate_orca_profile`、`_try_repair` 中 ORCA 专用判断和 `_reserve_attempt` 的策略选择到适配器/策略。主循环保留“调用策略→校验→保存→等待/执行”的通用结构。纯粹把原 if engine==orca 原封不动搬到 execution.py 不算完成通用委托。

### 6.4 保留原有参数与一次确认语义

多步 Plan 在展示一次整计划确认前，应尽可能准备所有已知参数；未来几何端口通过已声明的几何保留关系追溯已验证原子信息，不要求未生成文件提前存在，也不让模型补几何。

显式参数、配置默认、结构事实来源和 q/M 完整性校验保持；计划有缺字段时先 waiting，不能启动 ORCA。程序化输入准备不等于 AutoDFT 式自适应 Step Planner；后者属于 R5。

修复选项来自当前 profile/operation 和用户禁止条件的交集。已知局部数值修复仍有界；不新增 B3LYP 修复范围，不改方法/电子态，不将任意内部 RuntimeError 交给模型改代码。

## 7. 核心合同四：runner、guard 和恢复

### 7.1 保护已有进程实现

既有 runner 已挂起创建进程、加入 Job Object 后运行 on_started，再 resume。R1 的生命周期 callback 写入失败必须走既有清理路径；清理后事实一路到 Run 收尾，不能上层误标成成功或仅“锁冲突”。

分别测试：spawn 前失败、创建后 assign 失败、on_started/save 失败、resume 失败、监测失败、parser 异常、cleanup 失败、guard 最终处理失败。异常保留原阶段；不能 catch 任意 RuntimeError 后一律按 RuntimeLock 失败处理。

### 7.2 清理未确认优先于成功标签

最终 ProcessFacts 需要核验 stop_confirmed、process_tree_empty、cleanup_unconfirmed 和 cleanup_error。主进程退出不等于整个 Job 树为空；请求发出取消不等于停止完成。

清理未确认：Run/attempt 标为 interrupted 或等价的已有非成功结果，保留 guard，阻断该数据根后续真实计算。guard 删除只能由匹配 execution_id 的控制链在事实允许时操作，不能为修复卡住而自动 unlink。

### 7.3 当前格式崩溃恢复矩阵

| 发现 | 处理 |
|---|---|
| prepared 但无足够 spawn 事实 | 不猜“从未运行”；结合 guard/日志检查，不确定则 interrupted、禁止自动重跑 |
| started 且确认仍由存活控制链管理 | 返回 busy/status，不接管、不重复执行 |
| 记录 PID 已被复用/创建时间不符 | 不终止该无关进程；保留审计并进入需核验 |
| 原 owner 崩溃、进程或子树状态不可确认 | 保留 guard、停止，要求授权的恢复检查 |
| 进程已确认结束且 Result 与输入均可验证，但 Run 指针未提交 | 在 owner 下显式修复索引，记录恢复原因；不重新启动 ORCA |
| 结果无法验证或文件损坏 | 留存原始文件，failed/interrupted，不发布成功值 |

恢复对照 execution_id、Run/Step/attempt、输入/工作目录、PID/创建时间以及可取得的进程树事实，不以一个 PID 决定终止或清锁。拿不到可靠树信息时保持未知而不是猜测结束。

这是 R1 生命周期恢复，不是自动迁移旧格式活动任务。后者仍按 pending 决议，不读取后直接改写用户旧数据根。

## 10. 验收方法与覆盖要求

配套 `R1_ACCEPTANCE_CASES.jsonl` 给出 40 条待执行规格，不是可直接运行的 pytest 文件。实现后必须为每条映射具体 nodeid/命令/证据。科学夹具使用当前已有支持范围，计划中的概念例子不是替代实际分子、电荷、自旋和容差的默认参数。

### 10.1 五组不可缺少的验收

1. **故障闭合：**RuntimeError/TypeError、Result/Run 写入瞬态与持续失败、错误 Result 归属、诊断/会话写失败。检查异常、进程、文件、current_results，而不仅回复文字。
2. **授权与并发：**两个确认一个启动、不同 Agent 相同 root/run、跨进程竞争、失效预览、direct advance/CLI 入口、取消前/后 spawn。复用 R0 取消保护。
3. **生命周期：**prepared 早于进程、started 事实来源、一次 attempt 记录、冻结 budgets、发布原子性约定、独立成功分支保留、重启不重置预算。
4. **现有科学能力：**SP/Opt/Freq 输入/解析/check、profile 范围、身份路线、原始几何、Opt→Freq/SP/距离依赖、查询不重算。
5. **结构与真实门：**非 ORCA 测试 policy 不改主循环即可使用共同生命周期；callable 不进入 prompt JSON；同一真实 ORCA 经新入口，包外安装可用。

### 10.2 先保存旧红灯，再转成普通绿灯

R1-A 对原 gap 文件运行 --runxfail，期望取得历史 5 fail/1 pass 的等价事实；实际数变化要说明。修复每一项后移除其严格 xfail，不保留 XPASS 作为“已经修好”的终态。没有真正命中注入点的测试不得计入通过。

对 race probe 的测试同步改动需附旧→新说明：移动的是同步位置，不是“两个调用仅一次执行”的目标断言。给失败路径增加普通未知异常反证，防止为了范围极宽的 except 或 xfail 让全部情况变绿。

### 10.3 成绩分层

离线生命周期、Windows 进程、真实 ORCA、真实模型分别记录。R1 不要求为了证明执行器而消耗一个大型真实 LLM benchmark；现有对话可用固定模型输出回放与 real-advance 保护。至少一条真实 ORCA 是总方案 R1 必需，不能用替身替代。

不要要求总 passed 必须等于 383 或某个固定数。随着 fixture/同步/参数化与新增覆盖变化，按 nodeid 和不变量追踪；5 个原缺口不应留在 xfail，零个普通失败，原 BC01–BC12 无退化。

## 12. 真实 ORCA 最小门

先核对当前可用 ORCA 版本、合法安装、profile 适用范围、分子 XYZ、电荷/多重度、输入 hash 和预算。优先使用仓库已有受验证的小样本；具体选择 H2 或水等只是可选建议，不未经确认新增科学设置。

最小链：

1. 新入口创建一次明确 SP 请求并准备有效输入。
2. 确认前启动数为 0；固定预览、资源和方法。
3. 明确授权，经过新共同 lifecycle 调用同一个 ORCA runner。
4. 检查真实输入、正常终止与 SCF/check、有限且语义正确的能量、版本、输入与结果 hash。
5. 查询同一结果/文件，不再启动 ORCA。
6. 汇总当前 attempt 与授权，证明没有隐蔽第二次计算。

真实小矩阵的多方法 Opt/Freq 全覆盖属于 R8；R1 同时必须跑现有 Opt/Freq 离线科学回归，并对任何涉及其输入/解析实质改变单独补真实验证，不允许借“小 SP 通过”掩盖被改坏的频率链。

重复确认的竞态压力测试优先用受控本地小子进程，避免为了测试去重实际启动两个昂贵化学任务。真实 smoke 验证入口一致性，不代替所有故障注入。

改变持久元信息前先明确旧记录政策。源码可以在隔离目录退回，科学结果不能按代码回滚顺便删除。新诊断/guard 元信息旧版本读不了时，不把旧程序直接指向新数据根。

提交前检查 staged diff，按授权推送指定重建分支；不强推、不合并 main、不执行下一阶段。向用户报告工程门、真实门、用户接受三项状态，不混为一个“done”。

## 14. 给开发模型的执行摘要

你只实施 R1：统一执行边界与可靠生命周期。先在当前远程 HEAD 做差异审查，并读取本方案、master_plan 和 preflight。优先关闭 R0 的四类 gap；保持真实身份推进和取消保护；再完成单一 owner、attempt/result 发布、Tool 策略委托、runner/guard/恢复的一致性。所有生产工具对应写入最终经过共同生命周期，不复制 ORCA 实现。

不实现 tasks、result_field、新对话语义、反思 Agent、知识库、新方法或新引擎。不升级依赖、不放松科学标准、不提高资源、不触碰旧数据。合理迁移测试的 Barrier 与 monkeypatch 注入点，必须证明新注入仍命中且不变量未弱化。

最后完成离线与 Windows 故障回归、包外安装，以及一条获授权真实 ORCA 经新入口的证据。缺真实条件明确 blocked。报告结束于 awaiting_user_acceptance，不自行进入 R2。
